# Spec 03: Fix the status-bar dot + render the live countdown as a status-bar icon digit

## Objective
Fix the rest-timer notification's status-bar icon rendering as a plain dot (confirmed via on-device screenshot, even after spec 02's `IMPORTANCE_DEFAULT` fix), and — going further, per user request — make the status bar show the actual countdown as a legible digit/number on the icon itself while a rest is active, matching the effect of third-party "countdown in status bar" apps.

## Background — confirmed root cause and confirmed-feasible technique (2026-07-11)
**The dot bug**: `RestTimerService.kt`'s `buildNotification()` calls `.setSmallIcon(R.drawable.ic_launcher_foreground)` (line 233). That drawable (`app/src/main/res/drawable/ic_launcher_foreground.xml`) IS already flat white on transparent (`android:fillColor="#FFFFFF"`), so color is not the problem — but it's a **108dp adaptive-icon-foreground layer**, designed with heavy built-in padding for launcher-icon masking (only the center "safe zone" is meant to render after the OS applies its icon mask/crop). Used directly as a notification small icon (which Android renders at a much smaller, differently-cropped size, ~24dp), the visible plus-shape becomes a near-invisible speck — this is very likely why it collapses to what looks like a plain dot in the status bar. **This is a sizing/canvas-convention mismatch, not a color problem** — the fix is a dedicated icon resource built for notification-icon conventions, not reusing the launcher's adaptive foreground layer.

**Live-digit-in-status-bar technique (confirmed via Perplexity research, cross-referencing multiple independent sources including Stack Overflow discussions of the real "Countdown in Status Bar" Play Store app)**: no third-party app can write real system text into the status bar itself (that surface is privileged SystemUI, confirmed — the Clock app's live text-next-to-clock chip is not replicable). What such apps actually do is **draw the countdown digits into a small bitmap and set that bitmap as the notification's small icon** via `NotificationCompat.Builder.setSmallIcon(IconCompat)`, re-posting the notification periodically as the number changes. This is a real, achievable, standard-API technique — not a workaround or hack.

## The fix
1. **New dedicated notification icon resource**: `app/src/main/res/drawable/ic_rest_timer_notification.xml` — a simple vector properly sized/padded for notification-icon rendering (a 24dp viewport with the shape filling the visible area per Android's notification icon design guidelines — flat white/alpha-only, adequate safe margin, NOT the 108dp adaptive-foreground convention). Use this as the fallback/initial icon (e.g., before the first countdown tick, or if bitmap generation ever fails) instead of `ic_launcher_foreground`.
2. **Dynamic countdown-digit icon while a rest is active**: a new function (e.g. `renderCountdownIcon(remainingSeconds: Int, context: Context): IconCompat`) that draws the remaining time as a legible number onto a small `Bitmap` (via `Canvas`/`Paint`, white text on transparent background, sized to match notification-icon dimensions) and wraps it via `IconCompat.createWithBitmap(...)` for `setSmallIcon()`. **Numeric format**: at notification-icon size (~24dp), a full "M:SS" display is likely too cramped to stay legible — default to seconds-only (e.g., "93") unless the implementer finds a legible way to fit "M:SS"; verify legibility against Android's actual rendered icon size, don't just assume based on the source bitmap's own resolution.
3. **Update the icon on the SAME cadence the countdown actually changes** (once per second while a rest is active) — this is specifically what the user is asking for (a genuinely live-feeling countdown, not spec 02's "static icon + accurate chronometer text in the shade only"). Battery/notification-spam concern: rest periods are short (typically well under a few minutes); a once-per-second icon update for that duration is a reasonable, bounded cost, not the kind of indefinite battery drain the OS's rate-limiting protections are meant to prevent — but confirm this in practice (see Verification) rather than assume no OS throttling ever kicks in.
4. **Revert to the static fallback icon (`ic_rest_timer_notification`) when no rest is active** — the dynamic per-second icon only applies while `RestTimerService`'s countdown is running; skip/dismiss states should show the plain static icon, not a stale number.

## File targets
- New: `app/src/main/res/drawable/ic_rest_timer_notification.xml` — dedicated, properly-sized notification icon (fallback/idle state).
- Modify: `app/src/main/java/com/jauschua/ironlogv2/service/RestTimerService.kt` — `buildNotification()` (use the new fallback drawable instead of `ic_launcher_foreground`; call the new dynamic-icon renderer while `remainingSeconds != null`), new `renderCountdownIcon(...)` function, and `shouldRefreshRestNotification()`'s throttle (this needs revisiting now that the icon itself must change every second — the previous throttle was tuned for spec 02's removed duplicate-text problem; re-derive it for "notify() once per second while active" rather than leaving stale 5-second-interval logic in place).
- New test(s) in `app/src/test/java/com/jauschua/ironlogv2/service/RestTimerServiceLogicTest.kt` for `renderCountdownIcon`'s pure numeric-formatting logic (NOT the actual `Canvas`/`Bitmap` drawing itself, which is Android-framework-coupled and untestable in this repo's plain-JVM-unit-test setup — separate the "what number string to render" logic from the "how to draw it" so the former is unit-testable).

## Edge cases
- **Icon legibility at actual rendered size**: a bitmap that looks fine at its source resolution can still render illegibly small once Android scales it to actual notification-icon dimensions on a real device — this must be manually verified on-device (screenshot), not assumed correct from the drawing code alone.
- **Very large remaining-second counts** (e.g., a 3+ minute rest = 180+, a 3-digit number): confirm the rendering doesn't overflow/clip at the icon's small canvas; if 3 digits don't fit legibly, consider minutes-only past some threshold (implementer's judgment, but state the chosen behavior clearly in code comments).
- **OS-level notification/icon update rate limiting**: some OEMs throttle how often `NotificationManager.notify()` visibly updates an icon, independent of the app calling it every second — if on-device testing shows the status-bar icon doesn't actually keep up with once-per-second calls despite the code doing so, that's a real OEM-level limitation to document, not a code bug to keep chasing.
- **Skip/complete states**: confirm the icon correctly reverts to the static fallback (not a frozen last-shown number) when the rest ends or is skipped.
- **Spec 02's removed duplicate "X remaining" text and the chronometer must be unaffected** — this spec only touches the icon, not the title/text/chronometer setup from the prior two specs. Verify `setUsesChronometer`/`setChronometerCountDown`/`setWhen` and the static content text remain exactly as spec 02 left them.
