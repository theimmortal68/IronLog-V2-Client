# Spec 01: Autoregulated giant-set rest + background-capable rest timer

Combines build-plan items **G** (autoregulated rest — hardest set in a giant set governs the duration) and **D+E** (background rest timer — foreground service, persistent notification, sound when unfocused), since G's actual logic lives inside the same rest-timer feature D+E's service wraps.

## Objective
1. Extend the existing tap-based rest-duration multiplier (`RestTimer.kt`'s `restSeconds()`) to giant sets — today it's explicitly bypassed for `isGiantSet=true`, using a fixed duration regardless of how hard any exercise in the round was.
2. Make the rest countdown survive backgrounding: an Android foreground service becomes the single source of truth for the countdown, with a persistent notification and an end-of-rest sound, so leaving the app (screen off, switching apps) doesn't lose the timer the way the current ViewModel-coroutine-based countdown does today.

## Background (confirmed via codebase exploration)
- `RestTimer.kt:29` — `restSeconds(baseRest, tierLabel, tap, isGiantSet)` already multiplies `baseRest` by a tap-derived factor (`TOO_EASY`→0.75x, `ON_TARGET`→1.0x, `TOO_HARD`→1.5x) for T1/T1b anchors, but **skips this entirely for giant sets** (confirmed at `RestTimerTest.kt:51-58` — the existing test locks in the current "giant sets are fixed" behavior; this spec changes that behavior on purpose, so that test needs updating, not just extending).
- `CaptureViewModel.kt:357-362` (inside `logWorkingSet`) is where rest starts today: it reads `tap` from ONLY the just-logged set (the round's trigger-owning/last exercise, per `shouldStartRest`, `RestTimer.kt:94`) and calls `startRest(restSeconds(...))`. This is the exact call site that needs to instead aggregate ALL exercises' taps for the round just completed.
- `_loggedSetActuals: MutableStateFlow<Map<Int, LoggedSetActual>>` (`CaptureViewModel.kt:79`) already holds every logged set's `(actualLoad, actualReps, tap)` keyed by `plannedSetId` — this is where the other exercises' taps in the same round are read from. No new capture mechanism needed, just new aggregation logic at the point rest starts.
- The current countdown (`_restRemainingSeconds`, `startRest`, `CaptureViewModel.kt:176-185, 457-471`) is a `viewModelScope.launch` coroutine ticker — tied to the ViewModel's lifecycle, does not survive process death/backgrounding. `RestAudio.kt`'s `RestToneCue` is driven by a `LaunchedEffect` in `CaptureScreen.kt:196-210` — only fires while the Compose screen is in composition.
- **No foreground service infrastructure exists in this repo at all** (confirmed: zero manifest `<service>` entries, zero hits for `foregroundservice|notificationcompat|startforeground|notificationmanager` anywhere in the codebase). This spec introduces it from scratch.
- `minSdk=26, targetSdk=35` (`app/build.gradle.kts`) — `NotificationChannel` is always available (API 26+, no gating needed); `POST_NOTIFICATIONS` runtime permission (API 33+) and `android:foregroundServiceType` + matching `FOREGROUND_SERVICE_*` permission (API 34+ requirement) both need explicit manifest/runtime handling since nothing exists today.
- Server DTO: `GroupOut.rest_seconds: Int?` (`CaptureModels.kt:40`) is the only rest-related field from the server — a single fixed base value per group. **No server/DTO change is needed for feature 1** — the aggregation is 100% client-side, computed from data the client already has.

## The fix — architecture decision
**The foreground service becomes the single source of truth for the countdown; the ViewModel observes it instead of running its own ticker.** This avoids two competing timers (one in the service for background survival, one in the ViewModel for UI) drifting apart. Concretely:

1. New `RestTimerService` (foreground service, `android.app.Service` + `startForeground`), holding the countdown state (remaining seconds, running/paused) as a `StateFlow` exposed via a bound-service interface (a `Binder` subclass returning the service instance, or a simple in-process singleton `StateFlow` the service publishes to and the ViewModel collects from — either is acceptable; the TDD implementer should pick the simpler one that keeps the countdown logic itself in a plain, directly-unit-testable class separate from the `Service`/`NotificationManager` Android-framework calls, per this repo's existing test convention of testing pure functions/ViewModel logic without an instrumented-test harness).
2. `CaptureViewModel` starts/stops/adjusts the timer by calling into the service (start with a computed duration, skip, +30s) rather than running its own `viewModelScope` ticker; it collects the service's `StateFlow` for `_restRemainingSeconds` instead of decrementing it itself.
3. The service posts a persistent `NotificationCompat` notification showing remaining time (updated at a reasonable interval, not necessarily every second — avoid excessive notification-update spam) and plays the existing `RestAudio.kt` tone-cue logic (warning/tick/done beeps) at the appropriate remaining-time thresholds, moved into or triggered from the service so it fires even when `CaptureScreen` isn't in composition.
4. Manifest additions: `<service>` entry with `android:foregroundServiceType` (pick the most accurate available type for a rest-timer/workout-tracking use case — likely `specialUse` with a declared reason string, since none of the standard types — media/location/camera/etc. — precisely fit; verify against current Play Store policy for this type via the exact declared-reason requirement), `FOREGROUND_SERVICE` + the matching type-specific permission, `POST_NOTIFICATIONS` (with the standard Android 13+ runtime-permission request flow — request when the user starts their first rest period if not already granted, degrade gracefully to in-app-only countdown if denied rather than crashing).

## Edge cases
- **A giant-set round where not all exercises have logged a set yet at the moment rest would start** (shouldn't happen given `shouldStartRest` only fires on the round's last exercise, but guard defensively): the aggregation should skip missing/not-yet-logged planned_set_ids rather than crashing or treating a missing tap as `TOO_HARD`/`TOO_EASY` by default — treat a genuinely missing tap as `ON_TARGET` (the existing default used elsewhere in `logWorkingSet`, line ~359) for aggregation purposes.
- **`POST_NOTIFICATIONS` denied by the user**: rest timing must still work in-app (the existing in-composition behavior as a fallback) — do not silently break rest timing entirely just because the background notification can't be shown; this is a genuine app-usability requirement, not an edge case to skip.
- **App fully killed (not just backgrounded) mid-rest**: a foreground service alone does not guarantee survival of full process death in all cases (OS can still kill it under memory pressure, rare but possible) — the spec does not require surviving a full process kill, only backgrounding/screen-off/app-switch, which `startForeground` does correctly protect against under normal OS behavior. Document this limitation rather than over-promising in the implementation.
- **Skip / +30s actions while the service owns state**: `skipRest()`/`addRestTime()` (`CaptureViewModel.kt:474, 480`) need to route through the service (stop it / extend its countdown) rather than mutating a now-nonexistent local ticker.
- **Multiple giant-set tiers with different rest baselines active in different rounds of the same session**: verify the aggregation is scoped correctly per-group (a T2 GS round's hardest tap must never leak into a T3 GS round's rest calculation) — this should fall out naturally from scoping the round lookup to the SAME `GroupOut`/tier, but confirm with a test.
